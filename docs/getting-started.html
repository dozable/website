Chapter 1

Getting started

Dozable runs teams of AI coding agents on your Mac.

Dozable runs teams of AI coding agents on your Mac. A workspace holds the agents, their chat room, the folders they work in and a brief that says what the work is for. Agents from any vendor (Claude Code, Codex and more) take on the work one unit of work at a time; each is recorded in a journal, and the lessons you approve carry into the next. You watch, talk to them in the room and decide what matters. You work through doz, a command-line tool, and a web dashboard (doz ui).

Where each agent runs is one setting of the workspace, not the first thing you decide: in its own Linux micro VM, held by macOS's sandbox to its folder on your Mac (fenced, the default for a workspace's agents), or as you. Start with the default; Sessions on this Mac and Sandboxes compare the choices.

What you'll have in about 15 minutes: a workspace with an agent in it, a chat room where you talk to it, and a folder it works in. Most of the time is a one-off download.

Know three things before you start:

  • Agents need an account. doz onboard uses this Mac's own Claude Code login by default. That login expires after some hours unless the Mac's Claude Code renews it; for unattended work, add a setup-token account (Agents and accounts).
  • Workers talk through chat. Turn it on with doz chat on. Without it you drive the agents yourself.
  • Long jobs need room. doz exec stops a command after 120 s unless you pass --timeout; start a long one in the background with doz run NAME -d.

The steps, one at a time, are below: Your first workspace.

If you are an agent setting this up for someone, read Workspaces and then Letting another agent drive Dozable first.

What you need#

  • A Mac with Apple silicon (M1 or later) running macOS 26 or later.
  • About 5 GB of free disk for the first image. Sandboxes share their disks with the image they came from, so each extra sandbox usually adds only megabytes.
  • An internet connection for the first setup.
  • Optional: Claude Code installed and signed in on your Mac. Your sandboxes can then use that login, with nothing to paste. You can use an API key or a long-lived token instead, or decide later. That login (the account mac) gives out access that expires after some hours, and only the Mac's own Claude Code renews it — Dozable never does. doz account keepalive always keeps it fresh: when it expires, Dozable runs the Mac's own claude once to renew it. It can't do that for a daemon started over SSH (the login keychain is locked there). For long unattended work, use a setup-token account instead: claude setup-token makes a token valid for a year, and doz account add NAME --setup-token adds it (Agents and accounts).

Install#

With Homebrew:

The install takes seconds (a prebuilt, signed doz) and ends with a hint: doz onboard. More on installing, upgrading and removing: Installing, upgrading and uninstalling.

Set up this Mac#

Setup happens once per Mac. It checks that your Mac can run sandboxes, connects your Claude account, and prepares the agent's image so your first sandbox starts in seconds. Do it in the terminal or in your browser; both do the same thing.

In the terminal:

At each question the recommended answer is already selected: press Enter to take it.

  1. Checks. Apple silicon, macOS, the virtualization permission, disk space. A required check that fails stops setup and says why; an optional one (Claude Code not installed, for example) is a warning.
  2. Base image. Node.js, the Linux system every tool runs on — Enter starts its download (about 380 MB) in the background, once; every tool you try is added to it. The next questions come at once.
  3. Models & keys. The sign-ins Dozable found on this Mac (Claude Code, Codex), then a key if you want one — Anthropic, OpenAI, xAI, Google or an OpenRouter key (it is never echoed). Enter adds none.
  4. Access, Folder rules and Settings — GitHub and your SSH agent (off unless you choose them), what .dozignore does, and the settings file. See Setting up this Mac.
  5. Usage statistics. What an official build sends — counts and ranges about how Dozable is used, never names, paths, contents or anything inside a sandbox — and where to see it exactly (doz telemetry show). Enter keeps them on; answer n to turn them off. A build from the open-source repository sends nothing and skips this step.
  6. Stay in touch (optional). Release news, tool news, early access and tips and tricks by email — skip it with Enter. See Usage statistics and sign-up.
  7. Your first sandbox. claude, pi or opencode — a name (claude) and a new empty folder (~/doz-workspaces/claude). Dozable waits for the base if it is still downloading (Ctrl-C leaves it running; doz onboard --status shows it again), adds the tool and attaches you to it. Going straight to a workspace? Answer none here (or run doz onboard --first none).

In your browser:

The dashboard opens on the setup wizard: the same steps — the base downloading at the foot while you answer — the Usage statistics switch (on unless you turn it off), an optional Stay in touch, and the First sandbox.

Details: Setting up.

What you just set up#

  • Each sandbox is a small Linux virtual machine, not a container, with its own kernel and disk. It can't see your Mac's files, apart from the one project folder you share at /workspace.
  • A workspace's agents run fenced on this Mac by default — no VM: macOS's own sandbox holds each one to its project folder, its own temp and caches, and Dozable's proxy for the network, with your Keychain closed. A preset or --worker-isolation vm puts them in micro VMs instead; Where an agent runs compares the three choices.
  • The Dozable daemon runs the sandboxes and sessions. It's a background program that the first command starts, and it keeps running when nothing is (the setting daemon.always_on, on by default; off, it exits once nothing runs). doz and the dashboard are remote controls for it.
  • Sandboxes and fenced sessions sit behind a network proxy on your Mac. A sandbox has no network card of its own: every connection goes through the proxy, which allows only what you permit, and logs it.
  • Your credentials never enter a sandbox or a fenced session. The agent sees a stand-in; the proxy adds your real login as each request leaves for Anthropic. An unfenced agent is the exception: it acts as you.
  • Two files hold your choices: ~/.config/doz/doz.toml (your settings for this Mac) and a project's doz_project.yaml (its sandbox). Everything else is kept by the daemon.

Your first workspace#

Four steps: set up this Mac, make the workspace, start it, and then give it its next unit of work.

  1. doz onboard checks this Mac and sets up the account your agents use (above). Once per Mac.

  2. doz workspace new NAME --preset … says what the work is: the brief, the folders, the workers, and a preset for where they run and what network they get — blank (choose yourself: fenced on this Mac, a locked network), research, swift-tests, mac-admin or remotion-video (what each sets up). Add --dry-run first: it shows what would be made, what would be refused and what the start would still need, each with its fix, and makes nothing. A worker needs chat on (doz chat on).

  3. doz workspace start NAME runs the set-up check (it lists every gap with the command that fixes it), posts your brief as your first message in the workspace's room, opens the first unit of work and starts the worker, in the place the preset chose. Watch it on the dashboard (doz ui, then the workspace on Home), or follow its room from a terminal: doz chat read hello --follow. Write in the room to talk to it.

  4. When it is done, finish it and go on. doz workspace finish NAME closes the unit of work and archives it — the room's messages, the agents' conversations, its journal. doz workspace run NAME "next goal" opens the next one, with every lesson you approved from the ones before:

More: Workspaces, Runs, the journal and lessons, and a worked example of a whole process in Bring your own process.

Usage statistics and sign-up#

Official builds (Homebrew, the release download) send anonymous usage statistics, so we can see what to fix and improve: at most once a day, counts and ranges about how Dozable itself is used — which commands ran and how often they failed (by exit code), which agents, bases and network presets new sandboxes use, the size of your setup as ranges, typical start and wake times rounded to 50 ms, how long sandboxes ran and slept and how long agents worked (as ranges), which features you used (the dashboard, the installed app, the dashboard on your network (doz ui --lan), folder rules, GitHub access, restore points, saved disks), which built-in image-preparation step failed, and your Mac's macOS version, chip family, memory and cores as ranges — with a random install id. Never a sandbox, image or project name, a file or folder name or path, anything inside a sandbox, anything you type or a program prints, a command's arguments, a host or website, an account, email or key. Our server adds your country from the connection and does not keep your IP address.

Setup tells you about them and lets you turn them off there and then: the Usage statistics step of doz onboard (or doz onboard --usage-stats off in a script) and of the dashboard's setup wizard. If you never ran the setup, the first command says so in one line instead. See exactly what would be sent, and turn it off with any one of these:

Signing up is optional: doz signup (or the setup's Stay in touch) asks for an email and what you want — release news, tool news (new and updated tools you can try), early access, tips and tricks. A confirmation email comes first; every email has a one-click unsubscribe, and your email is never linked to the statistics.

Builds from the open-source repository send nothing. The statistics and sign-up code is part of the official builds only and is not open source; this repository holds the list of what may be sent and every switch. The full policy: dozable.com/privacy.

A sandbox on its own#

You don't need a workspace to use one agent: a sandbox on its own is a single agent in its own micro VM, which you attach to and talk to in your terminal. A sandbox works on one project folder, shared into it at /workspace: the agent's changes appear on your Mac at once, and your editor sees them live.

doz init asks for the sandbox's name (from the folder's) and its image, and writes doz_project.yaml in the folder. It holds no secrets, so you can commit it: anyone who runs doz up in the project gets the same sandbox.

The first time, this creates the sandbox and starts it in a few seconds (setup prepared the image already). After that, doz up in the folder wakes the same sandbox. Either way it opens the agent in your terminal.

Detach, don't quit. Press Ctrl-] twice to leave the sandbox (once opens a small menu at the bottom: d detach · n next · p prev · s sessions · Esc back). The agent keeps running, and doz up brings you straight back to it.

Your terminal's title shows where you are, for example my-app · claude · 14:05, and goes back to what it was when you detach. Details: Projects and Terminals and sessions.

No project yet? doz new — or Quick add in the dashboard — makes a sandbox with every default and puts you in it: a free name like claude-sandbox, and its own folder in your projects folder (~/doz-workspaces/claude-sandbox). See The quickest way.

Talk to your agent#

You're now in Claude Code, inside the sandbox. Its first-run screens are done and it doesn't stop to ask permission for each command: inside a sandbox, the VM and its network are the boundary. (To have Claude ask first anyway, see recipes.anthropic.claude-code.approvals in the settings.)

Claude also knows where it runs. Ask it:

where are you running, and where is /workspace on my Mac?

It should tell you it is in a Dozable sandbox (a Linux VM on your Mac), that /workspace is your ~/code/my-app, that its network only reaches what you allow, and that your credentials are added by your Mac and never stored in the sandbox. It learns this from a short note Dozable gives it at every start. See Agents and accounts.

A few things work as you'd hope:

  • It can install system packages. The agent has passwordless sudo inside its sandbox, so sudo apt-get install -y … works (Debian-based images) — and never stops to ask questions.
  • Its clock is yours. A sandbox follows your Mac's time zone, even after it slept while you travelled.
  • Copying works. When Claude copies something, it lands on your Mac's clipboard and a notice says so.
  • Browser sign-ins work. If a tool in the sandbox opens a sign-in page, it opens in your Mac's browser, and the login completes. See Signing in from a sandbox.

Day to day#

A sandbox you're not using doesn't have to hold your Mac's memory. Each of these brings the agent back exactly where it was: same conversation, same running programs.

what happensmemoryback in
doz pause my-appfrozen instantlykept~1 ms
doz sleep my-appfrozen and saved to disk, so it survives a crashkept~0.3 s
doz hibernate my-appsaved to disk, and the VM stopsgiven back to your Mac~0.3 s

doz wake my-app, or simply doz up in the project folder, brings it back. doz ls lists your sandboxes; the dashboard (doz ui) shows the same thing with a live terminal for each.

doz shutdown is a real power-off: running programs end but the disk is kept. doz reset goes back to a fresh copy of the image. Neither touches your project folder or the agent's own settings and history. Details: Sandboxes and their lifecycle.

When the agent needs a website#

A sandbox has no network card of its own. Every connection goes through a proxy on your Mac that checks a short list of permissions and logs the connection. The Standard permissions let a coding agent talk to its AI model, update itself, install system packages and your language's packages, use GitHub and send its own error reports. Anything else is refused and logged.

In the dashboard, the sandbox's details show What the agent can do as switches, with a one-click suggestion when the agent was refused something. The agent can't change its own permissions; only you can. Details: What the agent can do.
