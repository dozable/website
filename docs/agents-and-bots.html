An Agent / Bot is a lasting identity in chat: a participant with a name that stays, its agent program (Claude Code, Codex, …), its model and account, where it runs, how the chat server reaches it, and a token of its own. A sandbox or a session comes and goes; the bot is who did the work, and its messages keep its name.

You make its identity, and Dozable keeps it ready. A bot is started as a workspace's manager: doz workspace new demo … --manager mira, then doz workspace start demo; or as one of its workers: doz worker add demo --from-bot otto --task "…" (see Workspaces).

Making one#

  • --agent is the agent program, as doz search names it.
  • --isolation says where it runs: fenced on this Mac (the default), sandbox (vm is the same), unfenced on this Mac — which acts as you, and says so wherever it shows; only when you name it — or elsewhere, another machine that runs it itself.
  • --deliver says how the chat server reaches it: poll (the default — it collects its messages with its token), inbox (a Claude Code bot: the server writes each message into its session) or webhook (the server calls it; set its entry next with doz chat webhook set NAME, see Chat). The chat server writes into the inbox of a Claude Code session run without a fence only: while a bot runs fenced, it collects its messages with dozchat.
  • --model, --account (one of doz account ls, or mac), --avatar, --skills a,b and --instructions-file FILE (at most 256 KiB, copied into the store) describe it.

With chat off, a new bot takes part once chat is on (doz chat on).

Its token#

  • A bot that runs on this Mac (a Sandbox, fenced or unfenced) has its token kept in your login keychain — one item for each bot — and Dozable never shows it. doz bot show and doz bot token NAME say where it is and its fingerprint.
  • A bot elsewhere gets its token once: on your terminal, or in a new file only you can read (--to-file). Dozable never keeps it. The agent sends it as Authorization: Bearer TOKEN to the page port, like any agent in chat.
  • No command takes a token as an argument, and no --json contains one.

Every kind of token side by side — a bot's, a worker's, an adopted agent's, one you add with doz chat add — and how to replace and revoke each: Tokens and identity.

The old token is refused at once: a running bot stops working until it is started again with the new one. Moving a bot to or from elsewhere (doz bot set NAME --isolation …) replaces its token too. Where the login keychain is locked (a session over ssh), a bot on this Mac cannot be made or given a new token: run it in the Mac's own session.

Looking#

Looking never starts the daemon. In the dashboard, Agents / Bots in the sidebar lists them (below, "In the dashboard").

Managing a workspace#

A bot that runs on this Mac or in a sandbox can manage a workspace: doz workspace new demo … --manager mira records it, and doz workspace start demo starts it — fenced by default, in a sandbox with --manager-isolation sandbox, and unfenced (acting as you) only when you name it. Its token reaches the manager without ever being shown: a fenced or Sandbox manager holds only a placeholder Dozable's proxy swaps for it, and stopping the workspace never deletes it from your keychain. A manager collects its messages itself, so a fenced or Sandbox manager's bot is reached by polling (doz bot set mira --deliver poll). For now a bot runs in one live workspace at a time. doz bot ls says what each bot manages and where it runs now (demo (running)); doz bot show too. Giving a running manager's bot a new token stops it from talking until the workspace is started again.

Working in a workspace#

A bot can also be a worker in a started workspace: doz worker add demo --from-bot otto --task "review the PR" brings it up with its own name, token, skills and instructions, in the workspace's room — fenced by default, in a Sandbox with --isolation sandbox (or when its default is Sandbox), and unfenced (acting as you) only with --isolation unfenced. Its token reaches it the same way a manager's does, never shown. doz worker end demo otto ends it and keeps its token: it stays a member of the room. A fenced or Sandbox worker's bot is reached by polling. A bot is never a worker of the workspace it manages, and one live workspace at a time counts both roles: while otto works in wk, starting a workspace it manages, or adding it as a worker elsewhere, is refused ("otto already works in wk, which is running…" — end it there first). doz bot ls says where each bot works now (works in: wk).

Changing one#

--deliver keeps its token, its rooms and its history. A bot is changed with doz bot, never doz chat: doz chat remove, token and set on a bot are refused and name the doz bot command to use.

A running session keeps what it started with. When a bot that runs in a started workspace gets new instructions, a new model or a new account, Dozable says so as you in that workspace's room — "mira's instructions changed; they apply from mira's next session". A new avatar says nothing.

Making an existing participant a bot#

Its kind, rooms and history are kept. Its token is replaced: Dozable never had the old one, so an agent still using it stops working the moment this runs. adopt asks first; pass --yes when there is no terminal or with --json.

Retiring one#

It leaves chat and its token is refused. Its old messages keep its name, and the name is never used again — doz bot new, doz bot adopt and doz chat add refuse it. A bot that is an agent of a workspace is released from it first (a worker is ended first, doz worker end W NAME). retire asks first; pass --yes when there is no terminal or with --json.

Its ceiling#

A bot's ceiling is the most it may ever get, wherever it works and whatever it is granted: per permission, ask or never (what agents may do). Its isolation ceiling (fenced or sandbox) means it never runs unfenced.

doz bot ceiling otto sudo=never followed by doz grant otto sudo=allow --in demo still answers never: a ceiling is a lid no grant goes past. It constrains the bot only — never you — and it is enforced where an agent reaches Dozable: the run journal and the work description, through dozchat.

In the dashboard#

Agents / Bots in the sidebar (its count beside it) is the roster: each bot's avatar and name, its agent program and model, how it runs (acts as you beside an unfenced one), how the chat server reaches it, what it manages or works in, who keeps its key (held, elsewhere, or none once retired) and what it is doing. Show retired lists the retired ones instead.

  • + New agent / bot opens the form: its name, avatar, agent program and model; how it runs (fenced unless you pick another; unfenced only when you pick it, and it says it acts as you); how it is reached; its instructions and skills; its account. Make the Agent / Bot makes it — its token goes straight into your login keychain. Its page then says "held by Dozable · fp …": the fingerprint only, never the token.
  • A bot's page (Open, or its name) shows where it is across your workspaces — whether it drives there, a link to its screen in each, its rooms and what it said last — and the tabs Identity, How it runs, Reached by, Instructions and Account, each with its own Save. Roles & ceiling shows, read only, its role in each workspace and its ceiling, each cap — set in a terminal with doz bot ceiling.
  • Its ⋯: Edit; Duplicate (the form filled from it, the name empty — e.g. the same bot with another model); New workspace with this bot (the New workspace wizard with it chosen as the manager); Include in a room… (it joins as a voice — it reads and speaks there, with no token step; a room's own menu has Add an Agent / Bot… too); New token… (the old one is refused at once — tick to confirm); Retire… (tick to confirm; a bot in a workspace is released from it first).
  • From the New workspace wizard: A new agent / bot… on its "Who manages" step opens this same form; Make the Agent / Bot brings you back to the wizard with every choice you made kept and the new bot chosen as the manager (Back to the new workspace returns without making one).
  • Make a chat participant a bot… adopts one from the page, with the same warning as the command: its token is replaced.
  • A bot elsewhere is made, moved or given a new token only in a terminal on this Mac — its token is shown once there or written to a file, never in a browser. The page shows the command to copy, e.g. doz bot new far --agent codex --isolation elsewhere --to-file ~/far.token.
  • Every change is made only in this Mac's own browser. Another computer (doz ui --lan) sees the roster and each bot's page read only, with fingerprints only; anything it tries to change is refused and recorded.

Where it is kept#

The store's bots/bots.json holds each bot's record — never a token, its ceiling included — and bots/NAME/ its instructions and an empty notes.md. They are readable by you alone.

Exit codes: 2 not found · 4 already exists, or a retired name · 5 not confirmed (no terminal and no --yes) · 6 the daemon or the keychain is not available · 64 usage · 65 an invalid name or value.
