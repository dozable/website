This Mac's settings are in one file, ~/.config/doz/doz.toml (under $XDG_CONFIG_HOME when that is set). The file lists Dozable's own settings with a description and their default, commented out; only the values you set are uncommented. A recipe's own settings — the settings of the agent it installs: its version, approvals, memory_mib, network, history, and any the recipe declares — are a [recipes.VENDOR.PRODUCT] block ([recipes.anthropic.claude-code]), written only while one of them is set, so the file stays small however many recipes there are; doz config show --agent ID lists them. The dashboard's Settings page shows and edits the same file, and its Recipes section lists the recipes on this Mac.

Where a value comes from#

For each setting, the first of these that says something wins:

  1. a command-line flag (for the settings that have one — --store, --progress, --color/--no-color, doz create --cpus, doz create --approvals, …);
  2. its environment variable (DOZ_STORE, DOZ_PROGRESS, DOZ_COLOR, DOZ_DAEMON_IDLE, DOZ_SCREEN_CAPTURE, DOZ_BOOT_LOGS, DOZ_SUBNET, DOZ_KERNEL, DOZ_KERNEL_CACHE);
  3. the sandbox's own value (a setting one sandbox can have, below);
  4. its project's (doz_project.yaml: when the sandbox is made, and again at every doz up);
  5. this Mac's (the file);
  6. the default — the recipe's own, for a recipe's settings; Dozable's, for the rest.

doz config show names the source of every value, and the dashboard shows the same word as a badge: recipe · default · Mac · project · sandbox · env · flag. A value fixed when a sandbox is made (its agent's version, memory, network, its CPUs) is recorded in it with where it came from; changing this Mac's value later moves no existing sandbox (doz reset NAME moves its version).

Read and change settings#

--agent takes a recipe's id (claude-code), a major (opencode@2) or its full name (anthropic/claude-code).

In the dashboard: Settings lists Dozable's settings with their value, default, description and source, and changes them in place (Default puts this Mac's value back to the default). Its Recipes section lists the recipes in use (a sandbox runs the agent) and the ones installed (a baked image of it is on this Mac, or you set one of its values); search the catalogue for the rest. A recipe's page has its settings, its baked images, its sandboxes and Uninstall. A value set by an environment variable, and the settings that name a folder on your Mac, are shown read-only there — change them with doz config set.

Per sandbox and per project#

sandbox.clipboard, sandbox.browser_bridge, sandbox.open_files, sandbox.ssh_agent, sessions.tmux, sandbox.agent_sudo, sandbox.audio and its agent's approvals and history can also be set for one sandbox (sound only between speakers and on — whether it has sound at all is chosen when it is made; see Sound):

Or when you create it (doz create --clipboard off --browser-bridge off --open-files off --ssh-agent on --tmux --no-agent-sudo --sound on --approvals ask), or in its doz_project.yaml (clipboard:, browser_bridge:, open_files:, ssh_agent:, tmux:, agent_sudo:, audio:, approvals:, history:).

Conversation history cascades one layer further: agent.history (Dozable-wide: keep or agent-default) → the agent's own history (follow, the default, or keep / agent-default) → the project's history: → the sandbox's own. The most specific value that is not follow wins, and doz config show --sandbox NAME says which layer it came from. What each value does in each agent — which file and key Dozable writes, or that the agent keeps its conversations by itself — is in Agents and accounts and in doz config show --agent ID. The sandbox page's Config tab shows the same: its overrides first, with this Mac's value beside each and Follow the Mac.

The names before 0.37.34#

The recipe settings had other names before 0.37.34 (images.claude_code_version, claude.permissions, images.claude-code.memory_mib, …; the table below lists them). They still work: the file is read with them, and doz config get|set|unset takes them and says the new name. The first change written after the upgrade moves them to their new names and keeps the file as it was, once, as doz.toml.0.37.bak beside it. A base with no agent (python, go) keeps the memory and network it had: defaults.memory_mib and defaults.network, set from Claude Code's old values.

"Use GitHub as you" is a permission, not a setting: doz net allow NAME github:as-you (and github:push), doz create --github read|push, github: in doz_project.yaml — see GitHub as you.

About the file#

  • The file is Dozable's. set, unset, init and the Settings page rewrite it whole, atomically, readable only by you. Comments you add aren't kept.
  • A mistake never breaks Dozable. An unknown key or a value of the wrong type is a warning (that line is ignored, the default applies). A file that doesn't parse at all is ignored — with the line that's wrong — and never overwritten until you fix it.
  • When a change applies is part of each setting: at once, for the next command, the next sandbox created, the next session, the next start or wake, or after doz daemon stop.

Not settable, on purpose#

The dashboard's security limits and checks (session and link lifetimes, request and connection caps, the Host/Origin/CSRF checks, the content policy); a browser terminal's one-use tickets and paste limits; the guest programs; and any credential. ui.terminals can only take something away.

daemon.always_on and daemon.idle_timeout_minutes decide together. They are listed side by side, and each description names the other:

daemon.always_ondaemon.idle_timeout_minutesthe daemon
on (the default)anystays running; the timeout is ignored
offN greater than 0 (the default is 5)exits after N minutes with nothing running
off0never exits by idling — warned

The last row earns a warning in doz config show, after doz config set or unset of either setting, under both rows of the Settings page, in doz daemon status and in doz doctor: Warning: daemon.always_on is off and daemon.idle_timeout_minutes is 0, so the daemon will not switch off by idling. Once it is stopped it does not come back until the next doz command runs. A daemon started where the login keychain is locked (over ssh) is never kept running whatever the two say: it exits after 5 minutes with nothing running.

daemon.login_item and the menu bar app. When the menu bar app's Start at Login is on, the app holds the login item: it sets daemon.login_item to on, and doz removes its own plist from ~/Library/LaunchAgents and adds none while the app's item is there — doz daemon login-item (and doz daemon status --json's loginItem.owner, app) says the menu bar app starts the daemon at login. Turning Start at Login off sets it to off. With the app removed, its item counts as gone: doz daemon login-item on adds doz's own again. (The menu bar app.)
