Tokens and identity

In chat, every agent is someone: a participant with a name, and a token that proves it.

In chat, every agent is someone: a participant with a name, and a token that proves it. The token is how the chat server knows who sent a message, and how Dozable knows which agent wrote a journal entry or proposed a lesson. This page gathers in one place who makes each token, where it is kept, how to replace and revoke one, and what a machine without a token can do. The rooms themselves are on Chat; lasting identities on Agents / Bots.

You never have a token. You take part through your own socket in the store, which only your own programs can open: the dashboard and the doz chat commands use it. A token is an agent's identity, never one of your keys, and nothing on the network acts as you.

The chat server keeps only each token's hash. No command takes a token as an argument, no --json contains one, and none is written to a record or a log. An export of a room, a run's archive and a journal entry are swept for live tokens: one found is replaced by "[a chat token of NAME, removed by doz]", and you are told whose it was, never the token.

Each store has its own participants and tokens (and its own chat ports): a token of one store means nothing to another (Resources and disk space).

An adopted agent's token#

Adopting a sandbox or a session into a workspace with chat on gives it a participant of its own, under its name in the workspace, and a token. Adoption changes nothing in the sandbox — its disk and its doz.json stay as they were — so the token is not written there. Instead, every session Dozable starts in that place from the adoption on is given the token and this store's chat address (CHAT_URL), as a worker's session is: a launch secret, which the session sees only as a placeholder.

  • A session already running when you adopt it does not have them until it restarts. doz workspace adopt says so, and prints the one command that hands the token over now.
  • doz workspace adopt W NAME --no-token makes no participant: the agent stays off chat.
  • doz workspace release W NAME revokes the token and removes the participant.

Replacing a token#

The old token is refused at once. A running agent stops being heard until it has the new one: a manager or a worker of a started workspace from its next start, a bot elsewhere when you put the new token on its machine. A worker's token you take this way is yours from then on: Dozable no longer replaces it at a start or revokes it at down.

A worker's token: new at each start#

A worker that is not a bot has a token the daemon makes for it, and a new one at every start — doz workspace start, doz workspace run and a wake of a stopped session — the one before refused from then on, so a token never outlives the sessions it was made for. It is revoked when the worker's session ends (doz worker end) and at doz workspace down; a lasting worker (one added with a name) keeps its identity and its place in the rooms, and its next start gives it a new token. doz workspace state W --json shows when each identity's token was issued (identities[].token.issuedAt) — a time, never the token (Workspaces). Moving a bot to or from elsewhere (doz bot set NAME --isolation …) replaces its token too, and so does making a participant a bot (doz bot adopt), because Dozable never had the old one.

A bot that ends as a worker (doz worker end) keeps its token and its place in the room. doz chat who lists every participant: its kind, whether it has a token, how it is reached and its rooms.

Agents on other machines, and a machine without a token#

The chat server listens on this Mac only (127.0.0.1) until you open it to your other machines over Tailscale:

An agent on another machine then needs three things: this Mac's Tailscale address, the chat port (doz chat status shows it; the page port is 8790 unless you moved it) and its own token. It sends the token as Authorization: Bearer TOKEN. Its replies go back to the same chat server the message came from — a reply posted to another Dozable's server (another Mac, another store) lands in that server's rooms, not this one.

A machine on your tailnet without a token:

  • can reach the chat ports only if it is named in chat.remote_agents; any other machine is not answered at all;
  • even then gets nothing without a token: on those addresses the page port answers only /agent/… calls and attachments, each with a participant's token, and the line port always needs one;
  • is never you: no one coming from there is the owner, whatever they send.

The dashboard on your network (doz ui --lan, The dashboard on your other devices) is a different door: a browser signed in as you, and serve.chat decides whether it may read or write chat. A browser that may write acts as you in chat.
