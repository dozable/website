Dozable session messaging

Claude Code sessions live in a Dozable sandbox, or, for macOS work, are held by Dozable on the Mac itself. Grok Bot's worker talks to a relay session, the relay messages each project session by name, and the human opens the very same terminal or uses remote control. Numbered stages match the runbook below. The bot's command for this is relay. On Dozable 0.37.44 and later, relay types and reads with doz sessions send and doz sessions screen.

Runbook

Every command shape below was run on the Mac on 12 Nov 2026 against throwaway sandboxes, first with Claude Code playing the worker, then by the real primary agent and its Cursor worker. Names such as agent-relay are the proposed ones; the probe used probe-… and proj-… names. project-a stands for a real project folder.

Rules of the road

What to keep, what to avoid, what is still open, and how remote control works.

Keep

  • One sandbox per group of projects, sharing their parent folder, with one relay session inside it. The relay can only reach sessions in its own sandbox.
  • Messages as the primary channel. The worker types only into the relay. Work sessions get Claude-to-Claude messages, labelled by sender.
  • Names on every session: claude --name X and --session X, the same word for both.
  • Read back after every send. If the text is still sitting in the input box, send Enter again.
  • Hibernate when idle. The next attach wakes the sandbox.
  • Save as you go. Finished outputs in deliverables/, then relay collect. A result that exists only in a sandbox is not delivered.
  • Retire, never delete. relay retire ends a team and deletes nothing. Removal is the human's.

Don't

  • Overwrite or submit unsent text on the input line that you did not write. An attached client, or a change in terminal size, is not a reason to stop. Direct keys into a work session stay limited to a blocked prompt or a slash command.
  • Rely on doz sessions --screen for a live read. It returns the last saved screen, and a fresh session has none.
  • Turn on tmux inside the sandbox. Dozable's docs say it hides agent status and limits Claude Code's keys.
  • Expect /rc to work in a stock sandbox. It needs the one-time setup first.
  • Widen a sandbox's network or sign in inside it without the human's say-so.
  • Run doz attach without a piped stdin from a worker. It waits for a keyboard.

Not yet verified

  • relay forward as a standing launchd job. It was run by hand with --once for each test.
  • The human attaching from a real terminal, the doz ui dashboard, or doz serve on another device. The second viewer in the probe was another piped client.
  • Opening a remote-control link from another device, and /rc across a renewal of the Mac's login.
  • A blocked session: none blocked, so detecting and answering one was not exercised.
  • A real repo as the workspace, and pushing or opening a pull request from inside (needs a GitHub permission the human grants).
  • Long or multi-line instructions typed as keys.

Remote control (/rc)

  • Stock sandbox: refused. Claude sees Dozable's placeholder in an environment variable and treats it as inference-only.
  • One-time setup: a credentials file inside the sandbox that holds only the placeholder, and claude started without the variable. The Mac's default login is used; it never enters the sandbox, and no network permission was widened.
  • Result: active in four sessions at once, and the same link was still reported after a 90-second hibernate.
  • This leans on behaviour neither Dozable nor Claude Code documents, so an update to either could break it.
